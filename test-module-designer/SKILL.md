# Test Module Designer（验证模块设计）

为一个项目**设计验证模块**：先判断项目类型，再选择恰当的验证形态，并把结果落地为项目根目录下的锚点文件。

- **可构建 / 可运行**的项目（代码、产品、工具、系统）→ **工程测试模式**，产出 `TESTPLAN.md`。
- **调研 / 研究 / 分析 / 评估**类项目（无可执行产物，交付物是结论、报告、方案）→ **质询提问模式**，产出 `INQUIRY.md`。

> 本技能是**通用模板**：不依赖任何特定 Agent 的私有记忆，验证方案仅存于项目内的纯文本文件，任何工具/协作者都可读取与版本化。

## 两种模式

| 维度 | 工程测试模式 | 质询提问模式 |
|------|------------|------------|
| 适用项目 | 有可执行/可构建产物 | 交付物是结论/报告/方案 |
| 验证对象 | 代码、接口、行为、性能 | 论点、证据、假设、逻辑链 |
| 核心手段 | 测试用例 + 断言 | 批判性问题 + 反例 |
| "通过"含义 | 用例全绿、覆盖达标 | 关键问题都有可靠回答 |
| 产出文件 | `TESTPLAN.md` | `INQUIRY.md` |

## 判定项目类型

按顺序判断，取第一个命中的：

1. 项目里存在**可运行/可构建产物**（源码、可执行脚本、服务、API、UI）→ **工程测试模式**。
2. 项目的**交付物是知识性结论**（调研报告、可行性分析、文献综述、市场研究、方案评估）→ **质询提问模式**。
3. **兼有代码与研究结论**（如算法论文 + 实现）→ 两种模式**都做**：代码走工程测试，结论走质询提问，两份文件并存。
4. 无法判断时，**先向用户澄清**项目的最终交付物是什么，不要臆测。

## 触发时机

1. **设计验证模块**：用户希望为项目建立测试/质询体系时。
2. **项目评审前**：交付、合并、汇报之前，用对应模式过一遍。
3. 已有锚点文件时：读取它并在其基础上补充/更新，而非重复另起。

## 工作流程 A —— 工程测试模式

```
测试设计清单：
- [ ] 1. 明确被测对象与其质量目标（正确性/性能/安全/兼容…）
- [ ] 2. 划分测试层级（单元 / 集成 / 端到端）与各层职责
- [ ] 3. 为每层列出用例：正常路径 + 边界 + 异常 + 回归
- [ ] 4. 定义测试数据、依赖桩/mock、运行方式与环境
- [ ] 5. 设定通过标准（覆盖率阈值、必过用例、性能指标）
- [ ] 6. 写入 TESTPLAN.md，向用户复述确认
```

要点：

- **每条用例可执行、可判定**：写清"输入 → 预期输出/断言"，避免"测一下登录"这类无法判定的描述。
- **边界与异常优先**：正常路径往往最不容易出错，重点覆盖边界值、空/超限输入、并发、失败回滚。
- **分层不重复**：单元测逻辑分支，集成测模块协作，端到端测用户可见行为；同一问题只在最合适的层测。
- **可复现**：固定测试数据与随机种子，隔离外部依赖，确保任何人任何时候跑出同样结果。
- 模板见 [testplan-template.md](testplan-template.md)。

## 工作流程 B —— 质询提问模式

```
质询设计清单：
- [ ] 1. 提炼项目要验证的核心论点/结论（1–5 条）
- [ ] 2. 针对每条论点，从下列维度生成质询问题
- [ ] 3. 标注每个问题的「期望证据」——什么样的回答才算过关
- [ ] 4. 找反例 / 竞争性解释 / 边界失效场景
- [ ] 5. 汇总为通过标准（哪些问题必须有可靠回答）
- [ ] 6. 写入 INQUIRY.md，向用户复述确认
```

**质询维度**（对每条核心论点逐一发问）：

- **证据**：结论基于什么数据/来源？样本量、时效、代表性如何？来源可信吗、可溯源吗？
- **假设**：隐含了哪些前提？前提不成立时结论是否崩塌？
- **逻辑**：从证据到结论的推理是否有跳步、以偏概全、因果倒置、幸存者偏差？
- **反例**：是否存在反例或竞争性解释？作者是否只挑了支持自己的证据（确认偏误）？
- **边界**：结论在什么条件下成立、什么条件下失效？外推到其他场景还成立吗？
- **可复现**：换个人、换份数据，能否得到同样结论？过程是否透明可审？

要点：

- **问题要尖锐、可回答**：好问题能逼出"证据或修正"，而非模糊表态。
- **期望证据前置**：每个问题都标明"什么回答算过关"，避免自说自话。
- **对事不对人**：质询针对论证本身，目的是让结论更可靠，不是否定作者。
- 模板见 [inquiry-template.md](inquiry-template.md)。

## 输出格式

- 工程测试模式 → 在项目根目录生成/更新 `TESTPLAN.md`。
- 质询提问模式 → 在项目根目录生成/更新 `INQUIRY.md`。
- 两模式并存时，两份文件都写，并在开头一句话说明各自覆盖的部分。
- 生成后向用户**复述验证结构与通过标准**，确认无误再收尾。

## 原则

- **先判类型，再选形态**：验证形态必须匹配项目交付物，别给报告写单元测试，也别给代码只做泛泛提问。
- **可判定**：无论用例还是质询问题，都要有明确的"过/不过"依据。
- **抓重点**：优先覆盖高风险、高不确定性的部分，不追求穷举。
- **可复现 / 可审**：验证过程透明，任何人可重跑或复核。
- **锚点鲜活**：被测对象或论点演进时，及时更新对应文件，而非放任其过时。
- **不阻断**：验证模块用于暴露问题、辅助判断，最终决策权交还用户。
